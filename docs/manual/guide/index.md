# 认识 ws-flow

**ws-flow 是一套模块化、可扩展的 WebSocket 双向通信架构。** 它将事件订阅、请求响应和流式任务组织成一套连贯的 API，也为协议适配、消息处理和执行调度保留清晰的扩展入口。

你可以从几行收发代码开始：订阅关心的事件，用 `await` 等待一次请求，用 `for await` 读取连续结果。当项目需要接入既有协议、复用消息处理规则或调整调度策略时，再组合相应模块，让通信层随业务一起成长。

## 让业务代码表达通信意图

在持续到达的消息里，通知、响应和任务进度常常交织在一起。ws-flow 负责筛选与分发、请求和结果的关联，以及任务结束后的回收；业务代码专注于要发送什么、收到后做什么。

| 你想做什么 | 发起方 | 接收方 | 常见场景 |
| --- | --- | --- | --- |
| 发送通知，订阅关心的事件 | `emit` | `on` / `subscribe` | 状态更新、日志、行情 |
| 发出请求，等待一个结果 | `request` | `handleRequest` | 查询状态、执行命令 |
| 发出请求，持续取得结果 | `requestStream` | `handleStream` | 任务进度、逐段生成 |
| 主动推送连续数据 | `stream` | `onStream` | 持续采样、批量传输 |

同一连接上的多个订阅可以独立筛选和消费消息。一次请求的响应会自动回到对应调用处，连续结果则归属于自己的流任务，无需在业务中反复维护监听器和请求标识表。

双向能力贯穿这套模型：Client 可以调用 Server，Server 也可以通过代表单条连接的 `Session` 调用 Client；两端共享请求、取消和流生命周期的规则。

## 默认即可使用，按需组合扩展

扩展能力围绕明确的职责展开。你可以只调整其中一层，继续使用原来的业务接口。

| 当你需要…… | 使用的扩展点 | 业务代码可以继续…… |
| --- | --- | --- |
| 收发纯文本或特定二进制格式 | **Codec**：负责编码与解码 | 使用普通收发与订阅接口 |
| 接入已有服务的消息约定 | **ProtocolAdapter**：解释事件、请求和流的语义 | 在对端协议支持的范围内使用统一 API |
| 统一日志、校验、数据转换等处理 | **插件与中间件管线**：将处理规则组合到收发阶段 | 保持处理器聚焦业务输入和结果 |
| 调整消息处理的顺序与并发策略 | **调度层**：将排队与帧处理策略独立出来 | 使用原有的通知、请求和流接口 |

插件可以集中封装一组处理规则，在需要的宿主中复用；调度层安排消息帧如何进入处理过程；共享内核持续负责请求关联、流状态和资源清理。扩展各有边界，业务无需跟着重新实现一套任务管理。

这些能力都有默认配置。配套使用 Client 和 Server 时，选择通信 API 即可开始；需要扩展时，再阅读[按需扩展](/guide/extensions)与[架构设计](/design/)。

## 适配你的接入方式

### 已有 WebSocket 服务：独立使用 Client

Client 可以独立接入第三方服务。默认 `generic` 模式保留对方的消息结构，用 `send` 发送业务数据、用 `subscribe` 筛选消息，无需让对方采用 ws-flow 的 Envelope。

如果服务已经有事件名或请求标识等约定，再添加协议映射。请求、流和远端取消需要双方协议共同支持，适配器负责衔接这些已有能力。

### 自建通信服务：Client 与 Server 配套使用

Server 默认采用 ws-flow 协议，Client 设置 `protocol: 'ws-flow'`，即可使用完整的事件、双向请求和流式任务。Server 还提供 Session、房间和目标筛选，方便将消息发给一个连接或一组连接。

浏览器 Client 使用原生 WebSocket，Node.js Client 使用 `ws`。连接环境由入口处理，业务层沿用同一套通信方式。

::: details 了解交付与取消的边界
`send` / `emit` 完成表示本地发送阶段结束；需要业务结果确认时使用 `request`。

取消是协作式的：本库结束等待、清理关联并抑制迟到结果，业务代码通过 `signal` 停止自己的工作。重连恢复连接，不自动重放通知、请求或流。

消息持久化、断点续传和跨节点连接分组由应用层负责。具体边界见[生命周期](/guide/lifecycle)与[架构设计](/design/)，配置细节见 [API 参考](/reference/)。
:::
