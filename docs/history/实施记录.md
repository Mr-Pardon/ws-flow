## 阶段 1：可运行与可验证基线

修复 Server 空入口、dist 输出不匹配、纯声明目录的运行时导出、声明缺失引用；明确内部包如何构建和发布，去除 Server 对旧 Client 的非必要依赖。

验收：严格检查项目声明；构建产物可加载；用原生 ws 测试端在本机随机端口完成真实收发；在仓库外验证打包产物，而不依赖 tsconfig paths 掩盖问题。

这一步不要求提前重构 Client。先建立公共契约，再用原生 ws 测试端和两个内核实例验证双向能力。

2026-09-20 实施记录：

- 7 个包使用独立 tsconfig 和 dist，按依赖顺序构建，包入口指向 JS 与完整声明。
- 补齐 Server / runtime-core 入口、纯类型导出和缺失类型引用；相对导入采用 Node ESM 可执行路径。
- 移除 Server 对旧 Client、runtime-core 对 ws 的依赖。Client 保留浏览器原生 / Node ws 的现有选择逻辑。
- 消费侧公开声明引用 ws，因此 Client / Server 的 @types/ws 放入依赖，而非仅开发依赖；它不等同于强制安装 ws 运行时。
- pnpm run check-types 通过（skipLibCheck=false）。
- 4 个基础行为测试通过；7 个本地 tarball 在仓库外安装后，公共导出、严格类型检查和同一组 4 个测试通过。
- 浏览器环境分支使用 Node 原生 WebSocket 配合模拟浏览器全局对象验证，真实浏览器打包及 Worker 尚未验证。
- 内部包仍 private；这是可运行基线，不表示任务内核缺陷已修复或达到正式发布条件。

新增 Client 边界：标准 Envelope 仅约束配套协议，通用 Client 保留原始业务消息，按 Adapter 能力启用事件、请求和流。

协议适配第一阶段已实现 ProtocolAdapter / RuntimeMessage、genericAdapter / wsFlowAdapter 和 RuntimeCore.send / emit。旧 Client 暂未接入。顺带修复无事件 Envelope 重复包装、priority / meta 被 undefined 覆盖、Server context 重新赋值丢失。详见《协议适配实现》。请求 / 流任务能力的完整契约仍按后续阶段实现。

验证：严格类型检查通过；仓库外安装 7 个本地 tarball 后，新适配器类型与全部 16 项测试通过，包含真实 socket 上的通用格式收发和 Server 回归场景。下一步先修复接收流隔离、消费阻塞和连接清理，再在稳定的适配边界上加入请求关联。

职责收紧与订阅阶段：Adapter 不再携带 builder，改用可选 stream.write 只编码流帧；ID 和 builder 归运行时。新增 RuntimeCore.subscribe 的原始消息筛选、独立快照、有界队列、取消与 scoped cleanup。严格类型检查、全部 25 项测试以及仓库外 tarball 安装后的同组验证通过。新订阅仍是内核能力，尚未接入旧 Client，也未等同于完整的连接关闭清理；请求任务和既有接收流问题继续按下列阶段推进。

## 阶段 2：核心正确性

修复流按连接隔离、消费与帧推进死锁、context 修改丢失、Envelope 重复包装与字段覆盖、错误信息丢失、广播排除失效、Observer 同步异常泄漏。

统一断连清理、流终态和队列上限；将已知缺陷变为回归测试，不仅测试成功路径。

验收：两个连接使用相同流 ID 时互不影响；自然的异步迭代用法不阻塞后续帧；错误可见，结束后任务和监听得到回收。

阶段 2 进展：已实现接收流按连接身份隔离、消费与帧调度分离、远端错误传递、有限缓冲与提前退出回收；新增 closePeer / dispose 并接入 Server 断连与关闭。默认调度改为按连接串行。发送流现已登记到运行时，支持断连 / dispose / AbortSignal 本地取消，并请求生成器 return；生成器内部等待需协作退出。具体契约和未完成边界见《接收流与连接清理》；阶段 2 仍未全部完成，队列总容量、远端取消等继续推进。

验证：全部 39 项测试、严格类型检查通过；7 个本地 tarball 在仓库外安装后，公共类型及同组 39 项测试通过，包含真实 socket 的接收流消费、断连回收和外部服务器接管释放。

发送流生命周期补充验证：新增 12 项测试，累计 51 项通过；严格类型检查及 7 个本地 tarball 的仓库外安装验证通过。覆盖首次发送失败、源错误与传输错误竞争、生成器等待期间断连、显式取消、排队帧抑制，以及真实 socket 上取消后连接仍可用。

## 阶段 3：单连接双向请求

单结果请求现已落地：RuntimeCore.request / handleRequest，Server 公共与 Session 局部 handleRequest、Session.request；为兼容旧事件 handle 保留独立入口。请求支持乱序关联、反向嵌套、可序列化错误、默认 30 秒超时、本地取消、每 Peer 1024 条双向独立容量上限与断连结算。Adapter 可选 request.write 仅做编码。远端取消、入站任务执行期限与流式请求仍待后续阶段；用法和边界见《单结果请求实现》。

后续进展：单结果请求的远端取消已实现。标准协议增加 request_cancel，自定义 Adapter 通过独立 request.cancel.write 选择是否支持。已进入 transport 的请求在取消 / 超时时尽力发送控制帧，对端终止入站 signal 并释放记录；本地结算不等待传输。主动流远端取消、入站执行期限和流式请求仍待推进。

取消阶段验证：新增 9 项测试，累计 81 项通过；严格类型检查及 7 个本地 tarball 的仓库外同组验证通过，覆盖真实 socket 双向取消、超时传播、取消前后传输顺序、同 ID 反向任务隔离和取消发送失败。

验证：新增 21 项请求相关测试，累计 72 项通过；严格类型检查、7 个本地 tarball 在仓库外安装后的公共 API 类型与同组测试通过。覆盖真实 JSON WebSocket 双向请求与断连、自定义协议、反向嵌套、同 ID 双向隔离、容量限制和中间件控制字段保护。

实现规范消息分类、请求关联表、唯一 handler 选择、成功 / 失败响应、超时与取消；Server 提供公共 handler 注册，Session 能主动 request。

验收：双方并发请求、乱序结果、同名事件、反向嵌套请求、发送失败、断连都按《任务与流生命周期》结算。

## 阶段 4：完整流与组合能力

单连接流式请求基线已实现：RuntimeCore / Session.requestStream 立即返回 StreamTask，Server / Session.handleStream 注册异步生成器处理器；共享请求身份、期限、容量上限和远端取消。已接入既有流中间件，覆盖开始前错误、流中错误、提前 break、缓冲溢出与取消后的生成器回收。空闲期限、主动流远端取消与多目标组合仍未实现，详见《流式请求实现》。

流式请求验证：新增 14 项测试，累计 95 项通过；严格类型检查、7 个本地 tarball 仓库外安装后的公开 API 类型与同组测试通过。包含真实 JSON socket 双向流式请求、自定义协议、并发流隔离、开始前 / 流中失败、模式冲突、总超时、提前退出和有界缓冲。

统一请求流、主动流和消费者；实现有界缓冲、提前退出取消与生成器清理；Sender 基于单连接任务实现固定目标集合的结果收集。

验收：远端流失败可被 for-await 捕获，慢消费者不会无限增长；多目标部分失败保留其他结果。
