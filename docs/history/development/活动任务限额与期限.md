# 活动任务限额与期限

`taskLimits` 限制内核同时登记的请求和流，`taskTimeouts` 为任务执行与流进度提供期限。Server、Client 与裸 RuntimeCore 使用同一套语义；这些配置可以与[等待队列限额](队列限额与取消.md)、[字节限额与发送水位](字节限额与发送水位.md)组合。

三个层次各有统计对象：队列统计尚未开始的调度项，传输预算统计预占的原始/编码字节，任务预算统计尚未结算的逻辑任务。任务额度释放后，忽略取消的用户 Promise、生成器、外部服务请求仍可能继续执行或占用内存，因此活动任务限额不是实际并发执行、CPU 或堆内存的硬上限。

需要限制真实业务执行量时，业务函数应配合 `signal`，或在业务函数入口使用持有到真实执行结束的执行池/准入额度。仅更换 WSScheduler 的并发数不能承担这一职责：请求处理器会脱离收帧调度继续运行，避免等待反向请求时阻塞接收。

## 配置入口与默认值

Server 的 `WSServer.create` 第二参数、`WSServer.takeover` 第二参数、`new WSServer` 选项，以及 `new WSClient` 选项均接受以下配置。裸 RuntimeCore 将它们放在构造参数顶层，与 `base`、`schedulers` 并列。

```ts
import { WSClient } from '@ws-flow/client/node'

const client = new WSClient({
  protocol: 'ws-flow',
  taskLimits: {
    maxActive: 128,
    maxActivePerPeer: 64,
    incomingRequests: { maxActivePerPeer: 16 },
    outgoingRequests: { maxActivePerPeer: 32 },
    incomingStreams: { maxActivePerPeer: 8 },
    outgoingStreams: { maxActivePerPeer: 8 }
  },
  taskTimeouts: {
    incomingRequestMs: 30_000,
    streamIdleMs: 10_000
  }
})

client.onIssue(error => console.error(error))
client.dispose()
```

示例数值仅说明用法，不是经过负载测试的通用建议值。

`maxActive` 是该内核实例跨连接的总数，`maxActivePerPeer` 是单个 Peer 的总数。四个分类还可以分别填写这两个字段；一次申请必须同时满足总预算与分类预算，不会因为配置了分类就绕过总预算。所有数量上限均要求正安全整数，不接受 `0`、小数或 `Infinity`。

| 分类 | 计数对象 | 默认上限 |
| --- | --- | --- |
| incomingRequests | 收到并登记的单结果请求、流式请求 | 每 Peer 1024 个 |
| outgoingRequests | 本地登记并等待结果的单结果请求、流式请求 | 每 Peer 1024 个 |
| incomingStreams | 对端主动发起的流 | 未配置时不限制 |
| outgoingStreams | 本地分配的主动发送流 | 未配置时不限制 |

顶层总预算、分类的跨 Peer 总预算及表中未列出的维度，默认均不限制。请求的每 Peer 默认值可以显式调整。Peer 按对象身份隔离；重新连接必须创建新 Peer，不能复用已关闭对象。

## 计数生命周期

出站请求先登记再进入发送管线，因此本地排队期间也占请求额度；入站请求在消息中间件与协议校验完成后、调用业务处理器前登记。单结果请求等待响应发送完成，流式请求等待结果流结算。

`requestStream` 在发起端只计入 `outgoingRequests`，在处理端只计入 `incomingRequests`。它的结果流不再额外占用主动流分类。主动接收流在有效的新 `start` 上申请额度；重复 `start` 不会重复计数，也不会替代原流。本地 `createSendStream` 从对象分配时占用 `outgoingStreams`，即使尚未发送，也必须结束或取消以释放额度。

正常终态、失败、超时、取消、迭代提前返回、Peer 关闭与内核销毁都会清理对应登记。释放是幂等的；迟到结果不会重新增加额度，也不能替已经关闭的任务结算第二次。订阅数量、普通通知及用户在任务外创建的工作不计入这四类。

## 任务超限的影响范围

任务容量不足只拒绝当前申请，不会因为这一种错误主动关闭连接或结束其他任务。

| 申请位置 | 结果 |
| --- | --- |
| 本地 request / requestStream | 本地失败，不发送这次请求 |
| 本地主动流对象分配 | 本地失败，不发送该流的起始帧 |
| 入站请求 | 不调用业务处理器，回复带 `CAPACITY_EXCEEDED` 的 request_error |
| 新的入站主动流 | 不创建消费者、不调用流处理器，尽力发送 stream_cancel |

远端反馈仍经过普通发送管线、队列和传输准入。如果反馈帧自己触发队列或字节/水位超限，宿主继续采用这些层已有的任务帧失败策略，可能关闭该连接。这与“活动任务容量不足本身不关闭连接”是两个独立阶段。自定义协议未提供取消能力时，主动流拒绝不能保证对端停止生产。

## 两种新期限与原有请求总期限

`taskTimeouts.incomingRequestMs`、`taskTimeouts.streamIdleMs` 都要求正整数且不超过 `2147483647` 毫秒；`undefined` 或 `null` 表示不启用。它们不替代发起方原有的 `request(..., { timeoutMs })`：请求总期限仍默认 30 秒，包含发起方排队、发送和等待整个结果的时间，`timeoutMs: null` 才会关闭该总期限。

### 入站请求执行期限

`incomingRequestMs` 在入站消息中间件处理完成、请求被接纳时开始，覆盖业务处理器、流式结果生成与响应发送；不包含此前的收包、解码或入站排队时间。期限不是每个结果分片重新计算一次的计时器。

超过期限会结束任务登记、取消处理器的 `ctx.signal`，并抑制迟到业务结果。单结果响应或结果流起始帧尚未提交时，使用 `request_error` 返回 `EXECUTION_TIMEOUT`；结果流已经开始时，使用同一请求/流身份的 `request_stream` 错误终态。已经提交的终态不会再补第二条终态；已经进入 socket 的消息也不能被撤回。

处理器应把 `ctx.signal` 传给支持取消的异步操作，并在长循环或生成器内部主动检查。超时不会强行终止任意 JavaScript Promise，生成器内部未完成的等待也可能推迟其 `finally` 执行。

### 流空闲期限

`streamIdleMs` 适用于主动流与请求结果流，但起点按角色区分：

| 角色 | 开始计时 | 何时续期 |
| --- | --- | --- |
| 主动接收流、请求结果消费者 | 接纳首个 start，进入异步流中间件前 | 有效 start/chunk 通过流中间件并被接受后 |
| 主动流生产者、请求结果生产者 | 发送流对象分配后 | start/chunk 成功完成发送后 |

请求结果消费者尚未收到 `start` 时，由请求总期限控制等待；空闲期限不提前开始。生产者分配后一直不发送，或卡在生成器/发送等待中，也会受到已启用的空闲期限约束。

重复起始帧、其他流的消息、普通通知、被过滤的分片和失败的发送均不续期。终态、取消和关闭会清除计时器。接收侧流中间件可读取 `ctx.signal`；期限到达会结束本库对该钩子的等待，迟到返回的数据不能进入消费者，但钩子内部的任意用户 Promise 仍需自己配合取消。

空闲超时使用 `STREAM_IDLE_TIMEOUT`。主动接收流会尽力取消对应生产者；请求结果消费者会结束请求并尽力发送 `request_cancel`；生产者在需要且仍能发送时通知对端错误终态。

执行期限与流空闲期限共享同一个任务终止入口，先被确认的失败结算一次。即使错误反馈仍在发送管线中等待，也不会被另一计时器覆盖或再次占用任务额度。空闲检查使用单调时钟，并在接收流钩子结束、发送帧提交之前复查已过的期限，避免长时间同步代码阻塞计时回调后放行迟到分片或终态。

`requestStream` 与主动发送 `stream` 的调用选项都可填写 `idleTimeoutMs`：省略时继承本端全局 `streamIdleMs`，`null` 显式禁用这一次本地流的空闲期限。

```ts
import { WSClient } from '@ws-flow/client/node'

const client = new WSClient({
  protocol: 'ws-flow',
  taskTimeouts: { streamIdleMs: 10_000 }
})

await client.connect('ws://localhost:8080')
try {
  for await (const chunk of client.requestStream('long-report', null, {
    timeoutMs: 120_000,
    idleTimeoutMs: 20_000
  })) {
    console.log(chunk)
  }

  await client.stream(
    'updates',
    async function* () {
      yield { ready: true }
    },
    { idleTimeoutMs: null }
  )
} finally {
  client.dispose()
}
```

这些选项只改变本端的计时器，不通过协议协商对端期限。例如关闭本地结果消费者的空闲期限，不会关闭服务端生产者自己的空闲期限或入站执行期限。

## 错误、观测与维护

`TaskCapacityError` 和 `TaskTimeoutError` 从 `@ws-flow/runtime-core` 导出。本地容量错误包含 `code: 'CAPACITY_EXCEEDED'`，以及 `kind`、`scope`、`limit`、`actual`、`budget`：`budget: 'all'` 表示命中顶层预算，否则是命中的分类；`kind` 始终表示本次申请的任务类别。`TaskTimeoutError` 包含 `EXECUTION_TIMEOUT` 或 `STREAM_IDLE_TIMEOUT`，以及 `timeoutMs`。

本库自动生成的任务容量/期限错误响应与错误终态仅序列化 code/message，远端看到的是 `RequestError` 或流错误；不能假定远端还能读取本地预算字段或保留同一个错误类实例。取消帧只表达对应任务取消，不携带本地容量/期限错误的诊断字段。

- Client 的 `onIssue` 接收本地原始任务错误。
- Server 的 `onIssue('resource_error', handler)` 提供原始 `error`、`session`、`direction` 和可选 `taskKind`。任务错误有分类，队列/传输错误不要求有 `taskKind`。任务错误的 direction 按任务归属确定：incoming 为 receive，outgoing 为 send；例如本端发起请求后接收结果流发生空闲超时，仍属于 outgoingRequests/send，并非表示错误发生在发送帧中。
- RuntimeCore 的 `useTaskErrorObserver` 接收 `{ peer, kind, error }`，该事件没有连接关闭含义。
- `core.getActiveTaskCount(peer?, kind?)` 读取当前登记数：两个参数均省略返回总数，只传 Peer 返回该连接总数，指定分类可查看分类计数。它不是历史峰值或真实执行中的用户代码数量。

共享原语位于 `packages/runtime-core/src/taskResources.ts`。请求归属由 `requests.ts` 管理，主动流归属由 RuntimeCore 与 ReceiveDispatcher 管理，流计时器由 SendStream/ReceiveStream 管理。扩展任务类型时，必须一起维护申请、各类结算、断连清理和迟到结果路径，不能只在入口判断一次数量。
