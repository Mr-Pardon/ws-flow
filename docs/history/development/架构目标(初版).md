# @ws-flow 架构设计蓝图（Architecture Blueprint）

> 历史设计蓝图。当前职责与 API 见[架构编排与设计说明](架构编排与设计说明.md)，本版交付边界见[首版交付范围](首版交付范围.md)。

## 一、设计目标

@ws-flow 的目标是构建一套：

> **可组合、可扩展、具备统一语义的 WebSocket 应用层通信架构**

核心能力包括：

- 统一消息语义（普通消息 / 流消息）
- 可插拔的中间件 / 插件体系（pipeline）
- 可扩展的调度层（scheduler）
- 对 client / server 的抽象统一
- 支持流式任务（stream）的完整生命周期管理

---

## 二、核心设计原则

### 1. 单一语义结构（Envelope）

所有通信统一为标准消息结构：

```ts
type WSEnvelope<T = any> = {
  event?: string
  data?: T

  streamId?: string
  streamState?: 'start' | 'chunk' | 'end' | 'error'

  priority?: number
  meta?: Record<string, any>

  id?: string
}
```

设计原则：

- 扁平结构（flat）
- 系统字段 vs 用户字段通过命名区分
- 所有消息（普通 / 流）统一结构
- protocol 仅负责编码，不参与语义

---

### 2. 6-Stage Pipeline（核心架构）

系统统一抽象为 6 个阶段：

```txt
receive → route → consumeStream → produceStream → send → transport
```

解释：

| 阶段          | 说明                          |
| ------------- | ----------------------------- |
| receive       | 接收原始消息，解析为 envelope |
| route         | 路由匹配，触发 handler        |
| consumeStream | 接收流消费                    |
| produceStream | 生成流                        |
| send          | 发送前处理                    |
| transport     | 最终发送                      |

---

### 3. 职责分离（Separation of Concerns）

核心原则：

> **流程控制、数据处理、状态管理彻底解耦**

---

## 三、核心模块划分

### 1. Dispatcher（调度入口层）

#### SendDispatcher

```txt
envelope → scheduler → send pipeline → transport
```

职责：

- 统一发送入口
- 管理 send middleware
- 对接 scheduler

---

#### ReceiveDispatcher

```txt
raw → resolveEnvelope → scheduler → receive pipeline → route / stream
```

职责：

- 统一接收入口
- 分发普通消息与流消息
- 控制 route / stream 触发

---

---

### 2. Scheduler（调度层）

目标：

> **任务调度策略可插拔**

默认策略：

- session 串行
- priority 优先级

支持未来扩展：

- 并发控制
- 限流
- 队列策略

---

### 3. Stream 层

#### WSSendStream

职责：

- 将 generator 转换为标准流 envelope
- 自动生成生命周期（start / chunk / end / error）

```txt
generator → envelope → SendDispatcher
```

---

#### WSReceiveStream

职责：

- 接收流消息
- 管理生命周期
- 对接消费模型（consumer）

---

#### （未来）StreamConsumer

职责：

- 抽离消费模型（队列 / 策略）
- 统一 client/server 行为

---

### 4. Pipeline（中间件 / 插件层）

当前形态：

```ts
composeMiddleware(...)
```

目标形态：

```ts
plugin.use({
  onReceive(ctx),
  onSend(ctx),
  onStreamStart(ctx),
  ...
})
```

---

### 5. Session 层（待解耦）

当前问题：

- 强依赖 server
- 职责混杂（state + transport + dispatch）

目标结构：

```txt
SessionCore（纯状态）
Session（能力代理）
```

---

### 6. Protocol 层

职责：

```txt
encode / decode
```

约束：

- 不参与语义
- 不影响 pipeline

---

## 四、数据流统一模型

### 发送

```txt
API → envelope → SendDispatcher → scheduler → middleware → transport
```

---

### 接收

```txt
raw → resolveEnvelope → ReceiveDispatcher → scheduler → middleware → route/stream
```

---

### 流发送

```txt
generator → WSSendStream → envelope(start/chunk/end) → SendDispatcher
```

---

### 流接收

```txt
envelope → WSReceiveStream → consumer
```

---

## 五、API 设计原则

### 1. 用户只接触“语义 API”

```ts
session.emit('chat', data)
session.stream(generator)
```

---

### 2. 内部统一为 envelope

```ts
_dispatchSend(envelope)
```

---

### 3. 不暴露协议细节

用户无需关心：

- streamId
- streamState
- priority

---

## 七、当前重构阶段（重要）

当前处于：

> **“解耦 + 抽象阶段”**

---

### 已完成

- scheduler（基础能力）
- send pipeline
- stream send / receive 基础实现

---

### 正在进行

- Dispatcher 抽离
- envelope 统一
- stream 生命周期规范化

---

### 待完成（关键）

1. SendDispatcher 拆离
2. ReceiveDispatcher 拆离
3. Session 解耦
4. StreamConsumer 抽象
5. plugin pipeline 升级

---

## 八、设计约束（必须遵守）

### ❌ 禁止

- 模块直接访问 `_server.xxx`
- stream 直接操作 server 内部状态
- middleware 跨层级影响 scheduler

---

### ✅ 必须

- 所有通信走 envelope
- dispatcher 作为唯一入口
- scheduler 与业务解耦
- stream 生命周期标准化

---

## 九、未来演进目标

最终形态：

> **WebSocket 应用层运行时（Runtime）**

具备能力：

- 插件生态
- 流式处理标准
- 可观测性（trace / metrics）
- 多端统一抽象

---

## 十、总结

@ws-flow 的核心不是：

❌ WebSocket 工具库  

而是：

> ✅ **一套可扩展的实时通信架构协议与运行时系统**
