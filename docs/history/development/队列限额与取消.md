# 队列限额与取消

本文描述已实现的等待队列限制。原始消息字节限制和发送水位另见[字节限额与发送水位](字节限额与发送水位.md)；活动请求/流上限和执行/空闲期限见[活动任务限额与期限](活动任务限额与期限.md)。

## 配置与计数

Server 和 Client 支持 `queueLimits.receive` / `queueLimits.send`，各自包含：

- `maxQueued`：该方向、该调度器实例中尚未开始的任务总数。
- `maxQueuedPerPeer`：其中属于同一 peerId 的尚未开始任务数。

两者均要求正安全整数。未填写的维度保持无限额，以兼容现有使用；要启用保护，必须显式配置。运行中的任务不占等待额度，因此它们也不是最大并发数或全部内存上限。以下数值仅展示配置，不是经过负载测量的通用推荐值。

```ts
const limits = {
  receive: { maxQueued: 512, maxQueuedPerPeer: 32 },
  send: { maxQueued: 512, maxQueuedPerPeer: 32 }
}

const server = WSServer.create({ port: 8080 }, { queueLimits: limits })
const client = new WSClient({ protocol: 'ws-flow', queueLimits: limits })
```

Server 默认入站/出站各自使用一个 SessionScheduler；队列总限额跨该 Server 的会话共享。Client 入站将原始消息解码与内核分发放在同一有界队列，避免异步 codec 的 Promise 链积压绕过限额。Server 当前 codec 同步解码，不提供异步解码队列；两端均可另配 transportLimits，在解码之前检查单条和积压字节。

若 Server 某方向传入自定义 scheduler，不可同时配置该方向 queueLimits，构造时会报错；应在自定义 scheduler 自己设置限额。后续调用 setScheduler/setInScheduler/setOutScheduler 更换策略时，新策略负责自己的限额，旧队列不会迁移。关闭仍通过每个任务的 signal 通知原调度器。

## 超限行为

QueueCapacityError 从 `@ws-flow/scheduler` 导出，包含 `code: 'QUEUE_CAPACITY_EXCEEDED'`、`scope: 'global' | 'peer'`、`limit`、`peerId`。超限不会覆盖旧任务或静默丢弃消息。

| 场景 | 当前行为 |
| --- | --- |
| 普通出站 send/emit 无法入队 | 仅拒绝该次调用，连接继续可用 |
| 入站消息无法入队 | 关闭受影响 Peer 和 socket，清理其请求、流和排队工作 |
| 带任务身份的出站帧无法入队 | 同样关闭受影响连接，避免对端永远等不到结果/终态 |

最后一项采用保守策略：包括尚未发送的新请求或流起始帧。当前不进一步区分“对端已经知道的任务”，也不通过高优先级让控制帧越过其 start/request。后续如增加有限控制保留额度，必须保留同任务因果顺序。

Server 通过 `onIssue('resource_error', handler)` 提供 error、direction、session；Client 通过 onIssue 提供 QueueCapacityError。内核使用 `useQueueErrorObserver(info)`，其中 fatal 表示 Peer 已被内核关闭，自定义宿主需随即关闭真实传输。内核无法替宿主关闭 socket。用户观察器异常不会替代原始失败，也不会阻止清理。

关闭不会等待用户中间件结束或业务观察器完成。远端依赖 socket 断开来结算无期限任务；真实传输断线通知仍受网络时延影响。

## 取消与清理

内置调度器接受 `WSTask.signal`：入队前已取消则拒绝，排队期间取消会物理移除该项并释放计数，任务永不执行；开始执行后不假装用户 Promise 已停止，也不提前让后续同连接帧越过它。

Dispatcher 为每次工作连接调用方取消信号与 Peer 生命周期。closePeer/dispose 会及时结束调用者的等待，取消仍在原调度器中的排队项。收发中间件可观察 `ctx.signal` 协作退出；它属于本次分发，不替代请求处理器的任务 signal。

已经开始的中间件/codec/transport 如果不响应取消，仍可能保留资源和占据运行槽位。默认 SessionScheduler 可让其他 Peer 继续，但全局串行/并发策略可能被这样的工作占据。强制中断任意 Promise 不在本库能力内。

## 单独使用调度器

SessionScheduler(limits)、KeyedSerialScheduler(getKey, limits)、PriorityScheduler(limits)、ConcurrencyScheduler(concurrency, limits) 支持同样的等待限额并提供 queuedCount。ImmediateScheduler 没有等待队列，只有取消前置检查。

每个调度器实例独立计数；组合策略每层都有自己的等待阶段，不能把某一层限额视为整条组合链的唯一预算。peerId 缺失时，同类无身份排队项共享未指定 Peer 的额度；无 key 的 KeyedSerial/Session 任务直接执行。

第三方 scheduler 需要正确实现 signal、一次结算、一次执行和物理移除才能具备相同清理保证；仅接收接口类型不代表自动支持这些语义。

## 验证入口

tests/scheduler-resources 覆盖计数、非法参数、取消释放和顺序；runtime-resources 与 extra 覆盖分发取消、超限传播和关闭竞争；host-resources 用真实 socket 验证慢解码/中间件超限和连接隔离。运行 `pnpm test`、`pnpm run check-types` 与 `pnpm run verify-packages`。
