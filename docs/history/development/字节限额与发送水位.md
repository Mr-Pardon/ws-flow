# 字节限额与发送水位

Server 和 Client 现在可以限制单条消息载荷、接收与发送阶段的积压字节，并在原生发送缓冲较满时等待排空。这些限制与 `queueLimits` 的等待条数互补；它们属于本地资源保护，不构成对端消费确认或端到端流量控制。

## 配置入口

两个宿主都接受 `transportLimits.receive` 和 `transportLimits.send`。未配置的字节维度不设上限，未设置 `highWaterMark` 不启用水位等待。以下数值用于展示配置，不是经过负载测量的通用推荐值。

```ts
import { WSServer } from '@ws-flow/server'
import { WSClient } from '@ws-flow/client/node'
import type { ByteLimits, SendTransportLimits } from '@ws-flow/runtime-core'

const receive: ByteLimits = {
  maxMessageBytes: 64 * 1024,
  maxPendingBytes: 8 * 1024 * 1024,
  maxPendingBytesPerPeer: 256 * 1024
}

const send: SendTransportLimits = {
  maxMessageBytes: 64 * 1024,
  maxPendingBytes: 8 * 1024 * 1024,
  maxPendingBytesPerPeer: 512 * 1024,
  highWaterMark: 256 * 1024,
  lowWaterMark: 64 * 1024,
  waitTimeoutMs: 10_000,
  pollIntervalMs: 10
}

const server = WSServer.create(
  { port: 8080, maxPayload: 256 * 1024 },
  { transportLimits: { receive, send } }
)

const client = new WSClient({
  protocol: 'ws-flow',
  transportLimits: { receive, send }
})

client.dispose()
server.close()
```

Server 总字节额度跨本实例管理的所有 Session 共享；单连接额度按 Peer 对象身份隔离。Client 的同一组配置作用于该客户端实例，重连创建新 Peer。两个方向各有独立预算，两个宿主实例之间也不共享计数。

| 参数 | 含义 | 未配置时 |
| --- | --- | --- |
| maxMessageBytes | 单条完整消息的载荷字节上限 | 不限 |
| maxPendingBytes | 本方向已经预占、尚未释放的总载荷字节 | 不限 |
| maxPendingBytesPerPeer | 上述预占中属于同一 Peer 的载荷字节 | 不限 |
| send.highWaterMark | socket.bufferedAmount 加本帧字节数的准入上限 | 不等待水位 |
| send.lowWaterMark | 发生等待后允许恢复的原生缓冲水位 | floor(highWaterMark / 2) |
| send.waitTimeoutMs | 当前帧开始检查原生水位后的等待期限 | 10000 毫秒 |
| send.pollIntervalMs | 水位轮询间隔 | 10 毫秒 |

字节上限和高水位要求正安全整数；低水位要求非负安全整数且小于高水位。两个计时参数要求正整数且不超过 2147483647 毫秒，避免平台计时器溢出。`null` 不是无限额的表示方式。单独设置低水位或计时参数、没有高水位时会拒绝配置。

这些上限共同生效。若希望单条消息能达到 `maxMessageBytes`，还应让对应 pending 上限和高水位能够容纳这条消息。高水位小于单条消息时不会等待到超时，而是立即拒绝，因为空缓冲也无法满足条件。

## 计量对象和预占范围

这里的字节指 codec 边界的消息载荷，不是 JavaScript 字符串长度，也不是包含 WebSocket 帧头、TCP、TLS 等开销的网络总字节。文本按 UTF-8 计算，正确处理多字节字符、代理对和孤立代理项；ArrayBuffer 按 byteLength 计算，Buffer 和其他视图只计算当前视图覆盖的区间；Blob 按 size 计算；视图数组按各段相加。

`wireByteLength` 不会为了统计文本先分配一份完整 UTF-8 副本。启用计量后，不能识别为受支持载荷的自定义 codec 结果会明确报错；关闭字节限额和水位时不额外限制自定义传输值类型。

接收路径：

`socket message → 原始载荷计量/预占 → decode 与入站分发 → 释放`

Client 在异步 decode 排队之前预占，慢解码不会绕过字节额度。Server 在同步 decode 之前预占，随后保留额度直至该消息的内核分发结束。接收限额针对完整消息，业务请求处理器和流消费者脱离帧分发后继续运行的时间不计为这条原始消息仍在处理中。

发送路径：

`出站调度 → 中间件 → adapter → codec.encode → 计量/预占 → 水位准入 → send 完成 → 释放`

发送以中间件和 codec 实际产出的消息计量，因此会包含标准 Envelope、请求身份及流元数据。编码成功后，等待水位和正在发送的载荷均占 pending 额度。启用高水位且存在并发出站任务时，等待传输准入的已编码消息也保留预占。

出站调度器中尚未编码的对象不计入这份字节预算，应配合 `queueLimits` 限制等待条数。单条消息限制也发生在编码之后，不能阻止 codec 为一个巨大业务对象分配编码结果。接收解码后的对象膨胀、订阅快照、生成器状态和业务引用同样不按原始字节等比例计量，不能把 `maxPendingBytes` 当作整个进程的堆内存上限。

## 水位等待与发送顺序

设高水位为 H、低水位为 L、本帧载荷大小为 N，原生缓冲报告为 B：

- 首次检查时，B + N ≤ H 就允许发送。
- 一旦因空间不足等待，恢复必须同时满足 B ≤ L 和 B + N ≤ H。
- N > H 立即报 `MESSAGE_TOO_LARGE`，不会等待。
- 缓冲迟迟不能满足条件时，在等待期限后报 `SEND_BUFFER_TIMEOUT`；截止时间后才观测到的排空不能重新放行。

低水位避免缓冲刚腾出少量空间就不断暂停和恢复。若本帧较大，即使降到低水位仍可能需要继续等到有足够的整帧容量。

启用高水位后，宿主通过 `TransportSendQueue` 串行化同一 Peer 从容量检查到实际 send 完成的阶段。它独立于业务出站调度器，因此 Server 即使注入并发调度器，也不会让同一 socket 的多个帧同时检查并使用同一份容量。不同 Peer 仍可并行；同一 Peer 保留到达传输阶段的顺序，这不意味着并发中间件会按最初调用顺序完成。

`waitTimeoutMs` 从该帧轮到检查原生水位时开始，**不包括**此前的调度器排队、等待其他传输操作完成或运行用户中间件的时间。它不是普通 send 的端到端期限。请求自身的总期限与调用方 signal 仍独立生效；需要限制其他工作阶段时，应提供对应取消信号或协作式业务期限。

浏览器原生 send 返回表示提交到原生缓冲；Node 默认 ws.send callback 决定该次发送完成。两者均不表示对端业务已经消费。自定义 ClientConnection.send 应准确返回完成 Promise；若在实际发送结束前就返回，本库无法替它推断完成时间。

直接并发调用 `waitForWritable` 不会预占未来原生缓冲容量，自定义宿主需要同样组合 `TransportSendQueue`。直接绕过宿主调用原生 socket.send 的写入也不受本库门禁控制；其已有积压只能在后续 bufferedAmount 检查中被观察到。

## 取消与任务身份

RuntimeBase.transport 增加可选 `prepare(peer, message, signal)`，它返回 `{ send, release }`。宿主在 prepare 中完成编码、预占和准入等待。内核在准备完成后重新检查 Peer 和 signal，随后才标记任务开始真实传输并调用 send。

这样，仍停留在本地调度或水位等待阶段的请求被取消时，不会错误地向远端发送“取消尚未见过的请求”。已经开始发送的请求仍采用原有尽力远端取消语义。prepare 需捕获连接身份，不能在重连后把旧消息改投新 socket。

预占释放函数是幂等的；发送完成、准备失败、取消、断连都会走相应清理路径。关闭 Peer 后释放旧预算，再开始新连接时，旧操作迟到的 release 不能扣减新预占。等待中的水位计时器和 abort 监听会在结束时移除。

已经提交的发送或正在执行的用户 codec/中间件不能被强制终止。取消不假装一个未结束的发送回调已完成，也不让后续同连接发送越过它。连接关闭会清除逻辑预算，但一个不响应取消的用户 Promise 仍可能实际持有旧数据，因此预算归零不等于其所有内存已经释放。

## 错误与关闭策略

`TransportLimitError` 从 `@ws-flow/runtime-core` 导出，具有 `code`，以及适用时的 `limit`、`actual`、`scope`。scope 为 `message`、`global` 或 `peer`；并非每类错误都有数值额度和 scope。

| code | 触发条件 |
| --- | --- |
| MESSAGE_TOO_LARGE | 单消息额度或发送高水位容纳不下该消息 |
| PENDING_BYTES_EXCEEDED | 全局或同 Peer 的 pending 字节额度不足 |
| SEND_BUFFER_TIMEOUT | 原生发送缓冲在当前帧的等待期限内未满足准入条件 |
| INVALID_BUFFERED_AMOUNT | 启用高水位，但 socket 未提供有限、非负的 bufferedAmount |
| UNSUPPORTED_WIRE_DATA | 启用计量后，原始载荷或编码结果不属于受支持类型 |

非法配置在构造时抛 TypeError/RangeError。普通断连和调用方取消沿用其原有错误/取消原因，不统一包装成额度错误。

| 场景 | 行为 |
| --- | --- |
| 普通出站通知触发传输资源错误 | 拒绝本次发送，连接保持可用 |
| 入站触发字节资源错误 | 关闭受影响连接，清理其请求、流与排队工作 |
| 任意带任务身份的出站帧触发传输资源错误 | 保守关闭受影响连接，让两端待定任务得到终止 |

带任务身份包含尚未发出的新请求和流起始帧，不只包含响应或终态。资源不足时不静默丢帧，也不把某个任务失败伪装成成功。Server 只关闭受影响 Session，其他连接可继续使用已释放额度。

Server `onIssue('resource_error', handler)` 提供 error、direction、session；Client `onIssue` 提供原始错误。Client 主动因字节/水位资源错误关闭时使用应用关闭码 **4009**，等待条数超限继续使用 **4008**。显式启用重连时仍遵循重连策略，但不会重放旧业务任务。

内核 `useTransportErrorObserver` 提供 `{ peer, error, direction, fatal }`。出站资源错误由内核分类，入站原始字节检查由宿主执行。自定义宿主收到 fatal 时必须关闭真实传输；只清除本地请求表不能让远端及时结束等待。

## 解析器及其他资源边界

宿主字节检查在 WebSocket 已交付完整 message 后发生，此时解析器可能已经分配了消息缓冲。因此，Node ws 的 `maxPayload` 仍应独立配置：create 使用第一参数；takeover 场景在外部 WebSocketServer 上配置。解析器报错发生在更早阶段，不保证表现为宿主的 TransportLimitError。

对于压缩消息，本库计量的是宿主看到的载荷或 codec 产物，不是压缩网络包体。压缩过程、解析器内部队列、操作系统缓冲及浏览器内部接收内存不由 ByteBudget 接管。发送 pending 预算与原生 bufferedAmount 也是两个不同阶段的量，不能简单视为互相替代。

后续已实现登记中请求/流的共享可配置上限、流空闲期限与入站业务执行期限，见[活动任务限额与期限](活动任务限额与期限.md)。它们独立于本页的字节保护，也不提供接收方确认式流量控制。消费队列容量仍按原有契约执行；持续运行和压力验证仍需结合实际消息大小、并发数、处理器耗时及连接数量进行。
