# 协议适配与原始消息订阅

> 本页保留内核阶段记录。Client 已迁入共同内核，当前能力和入口见[架构编排与设计说明](架构编排与设计说明.md)及[Client迁移与使用](Client迁移与使用.md)。

2026-09-20。本文描述已实现的内核入口，区别于完整双向任务 API 草案。

## 已实现边界

```text
外部字节 -> 宿主 Codec.decode -> Adapter.read -> RuntimeMessage -> 接收管线 / 路由
内核消息 -> 发送管线 -> Adapter.write -> 宿主 Codec.encode -> 外部字节
```

Adapter 是同步的格式 / 语义映射，不负责 socket、JSON 编解码、重连或异步业务。异步处理仍放在 middleware / handler。Node ws 与浏览器原生 WebSocket 的选择不受 Adapter 影响。

RuntimeMessage 是内部处理信息，当前保留 event / data / streamId 等字段供既有执行链使用，但不要求外部服务采用这些字段。ctx.envelope 暂时保留旧名字，类型已改为内部 RuntimeMessage。接收 ctx.raw 保留 Codec 解码后的输入；发送 ctx.raw 保留 dispatcher 收到的内核消息。管线本身仍共享上下文，订阅分发则对每个分支创建消息快照。

Adapter 由宿主选择，RuntimeCore 负责装配；它仅在收发边界解释外部结构。调度、订阅队列、流生命周期不调用协议规则管理自身状态。

## 通用格式

```ts
import { RuntimeCore, genericAdapter } from '@ws-flow/runtime-core'

const runtime = new RuntimeCore({
  base: {
    protocol: genericAdapter({
      event: input => {
        if (typeof input === 'object' && input !== null && 'type' in input) {
          return typeof input.type === 'string' ? input.type : undefined
        }
      },
      writeEvent: (event, data) => ({ action: event, payload: data }),
    }),
    transport: { send: async (peer, message) => sendDecodedMessage(peer, message) },
  },
})

await runtime.send(peer, { action: 'start', job: 42 })
await runtime.emit(peer, 'start', { job: 42 })
```

示例中的 peer 和 sendDecodedMessage 由宿主提供。前者原样发送业务对象；后者通过 writeEvent 得到 `{ action: 'start', payload: { job: 42 } }`。

- 不配置 event 时，genericAdapter 只把输入作为 data，不猜测任何保留字段。
- 配置 event 只提取匹配信息；data 仍是完整原始消息。
- writeEvent 是独立的发送能力，不能因为能读取事件名就推断如何构造远端命令。
- priority / meta 可以控制内部处理，默认不注入通用模式的外部消息。
- 文本、数值、null、二进制等数据均可原样交给 transport；transport / Codec 负责格式是否适合实际 WebSocket。
- 缺少 writeEvent 时 emit 拒绝；缺少 stream.write 编码能力时 createSendStream 拒绝，抛 ProtocolCapabilityError。

这些入口属于 runtime-core。旧 WSClient 尚未接入新内核，不能直接将此配置传给旧 WSClient 构造函数。

## 标准格式与兼容

RuntimeCore 未配置 protocol 时使用 wsFlowAdapter。它保留现有标准格式；运行时另行创建自己的 stream builder，Server 当前继续采用此默认行为。

- `base.builder.envelope` 作为运行时 builder 扩展入口保留，默认 builder 在每个 RuntimeCore 构造时创建一次。
- 显式 `base.protocol` 控制网络格式，builder 控制内部消息构造；通用模式不会因为存在 builder 就偷偷开放标准流发送。
- adapter 在 RuntimeCore 构造时确定，本阶段不支持运行中替换协议。
- dispatcher.send.dispatch 接收内部消息对象，不再猜测输入是否是业务数据。发送任意业务数据应使用 runtime.send，现有 session.send 仍由 session 构建内核消息。
- wsFlowAdapter 接收端将含已知标准字段的对象识别为标准消息。这只适用于配套协议；有同名业务字段的外部服务应选择 genericAdapter。
- 无 event 的 `{ id, data }` 消息现在也正确识别，避免多套一层 data。
- 发送 options 仅覆盖明确提供的 priority / meta，不清空原消息字段。

规范消息会在适配后和管线结束后校验；非法字段与不完整流帧拒绝 dispatch。Server 通过现有 process_error 入口报告此类校验失败。已有 invalid_stream 观察入口仍处理缺失 start 等执行期问题。

## 自定义流协议

自定义 ProtocolAdapter 提供 read、write，并可选提供 `stream: { write(frame) }`。运行时 builder 产生内部流消息，stream.write 只把帧映射为远端格式；普通 write 不再处理流帧。Adapter 不分配 ID、不拥有计时器或任务记录。

read 可以显式提取远端流语义；stream.write 仅表示发送编码能力。单纯 read 能识别流，不代表对方支持本地主动发送流。

这是对上一轮未发布的 Adapter 草案的收紧：wsFlowAdapter 不再接受 builder 参数；自定义 adapter.stream 从 builder 改为编码钩子。现有 Server 的 message.builder 入口保留。

接收流的跨连接隔离、异步消费阻塞及断连清理已在后续阶段修复，详见《接收流与连接清理》。完整远端取消和背压仍待实现。

## 不配置事件解释的原始消息订阅

下面是已实现的内核 API，不是尚未重构的旧 Client API：

```ts
const runtime = new RuntimeCore({
  base: {
    protocol: genericAdapter(),
    transport: { send: async (peer, message) => sendDecodedMessage(peer, message) },
  },
})

const subscription = runtime.subscribe(raw => {
  return typeof raw === 'object' && raw !== null
    && 'type' in raw && raw.type === 'progress'
}, { capacity: 128, signal: controller.signal, peer })

for await (const message of subscription) {
  console.log(message.raw, message.data, message.peer)
}
```

peer、controller 和 transport 由宿主提供。genericAdapter 无需配置任何事件规则，原始业务字段即可参与筛选。泛用 Client 未来由宿主默认组装此适配器，无需让入门用户先了解 RuntimeCore。

- subscribe 返回有界的异步迭代器，默认容量 128 条；每个订阅各有一份队列，消费者之间不竞争数据。
- 在 receive 管线完成且未 stop 后分发。message.raw 表示此时原始解码输入，message.data 表示处理后的数据，message.event 是可选的语义信息。
- 对每个订阅用 structuredClone 复制 raw / data / event，再执行 predicate。数据应是可结构化克隆的消息；不可克隆值（例如函数）导致该订阅失败。共享内存值不属于隔离承诺，应由 Codec 转为独立缓冲。
- peer 保持真实连接身份，不复制连接对象；业务不要将它当成分支独享的可变数据。
- predicate 必须同步返回 boolean；异常、非法返回值只失败该订阅。异步业务处理放在消费循环中。
- 超出容量以 SubscriptionOverflowError 失败，清空缓冲，不静默丢失消息，也不阻塞其他订阅或接收链。
- cancel、AbortSignal 或 for-await 提前 break 均幂等地注销订阅，释放待处理读取；订阅取消不发送远端任务取消命令。
- `clearSubscriptions(peer)` 只清理显式绑定该 Peer 对象的订阅；跨连接订阅继续存在。无参数时清理全部。连接关闭应调用已实现的 closePeer，运行时退出调用 dispose；Server 已接入这两个生命周期入口。
- 当前分发普通消息，不把标准流帧逐条作为普通通知重复投递；通用协议未声明流语义的消息仍属于普通业务消息。

现阶段每条消息按订阅数复制数据，选择可预测的隔离行为而非零拷贝。高吞吐成本尚未做基准测试，后续优化不得悄悄取消隔离约定。
