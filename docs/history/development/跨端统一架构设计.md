# @ws-flow 跨端统一架构设计

> 历史设计草案。当前职责与 API 见[架构编排与设计说明](架构编排与设计说明.md)，本版交付边界见[首版交付范围](首版交付范围.md)。

## 一、背景

当前 `server` 侧已经逐步形成了较清晰的运行时内核：

- `pipeline`
- `dispatcher`
- `stream`
- `scheduler`
- `runtime + deps`

而 `client` 侧历史上更偏“接收侧优先”的设计：

- `route / subscribe` 能力较强
- `send` 能力相对较薄
- `watch` 当前仍承载较多订阅语义
- 数据格式依赖 `protocol` 解析

当前阶段的目标不是立即统一所有 API，而是先确定：

> 哪些能力适合跨端沉淀为统一内核，哪些能力应该保留为 `server/client` 各自的宿主适配层。

---

## 二、设计目标

跨端统一后的架构，应同时满足以下目标：

1. `server/client` 在内部尽量共享同一套数据流模型。
2. `client` 仍可独立使用，不能强依赖 `ws-flow/server`。
3. 与 `ws-flow/server` 配套时，`client` 可以进入严格模式，直接复用统一 envelope 语义。
4. 后续 `plugins pipeline` 可以挂在统一内核层，而不是只能挂在某一端。
5. `client` 可以在 major 重构中调整内部链路，但高阶 API 仍保持易用。

---

## 三、统一原则

### 1. 统一“运行时内核”，不强行统一“宿主 API”

适合统一的层：

- `pipeline`
- `dispatcher`
- `stream core`
- `scheduler`
- `protocol adapter contracts`

不建议直接统一的层：

- `WSServer`
- `WSSession`
- `WSClient`
- `route / subscribe / watch` 的外部 API 形态

原因：

- `server` 天然是“会话主导、分发主导”的宿主。
- `client` 天然是“连接主导、订阅主导”的宿主。
- 两侧外部职责不同，但内部的消息执行内核可以高度一致。

### 2. 统一“消息生命周期”，不强行统一“入口形式”

跨端最值得统一的是消息从进入系统到离开系统的生命周期：

```txt
decode -> dispatch -> schedule -> pipeline -> route/stream -> encode/transport
```

而不是强迫两端必须使用相同的 API 命名或入口方式。

### 3. `protocol` 必须保留，但要产品化

`server` 可以约束数据结构，因为它是主控侧。  
`client` 不能要求所有用户都接受同一种消息结构，因此：

- `client` 必须保留 `protocol` 或等价的 adapter 层
- 但不能把大量底层 resolve 函数直接暴露成高门槛配置

应改造成两种模式：

- `strict mode`
- `generic mode`

详见后文。

---

## 四、跨端统一分层

建议将整体划分为两层：

### 第一层：统一运行时内核

这一层是未来真正适合复用和拆包的部分：

```txt
pipeline
dispatcher
stream core
scheduler
protocol contracts
```

职责：

- 描述消息如何被处理
- 描述流如何被生产和消费
- 描述任务如何被调度
- 描述协议如何适配不同数据格式

### 第二层：宿主适配层

这一层保留在 `server/client` 自己的包内：

```txt
server:
  WSServer
  WSSession
  rooms
  ws transport adapter

client:
  WSClient
  route / subscribe / on / once / watch
  ws-event-proxy adapter
  reconnect / watch task restore
```

职责：

- 提供面向用户的高阶 API
- 组织 runtime 组装
- 连接具体 transport / proxy / room / reconnect 等宿主行为

## 五、统一后的双端数据链路

### 1. Server 数据链路

#### 接收链路

```txt
transport
-> protocol decode
-> receive dispatcher
-> scheduler
-> receive pipeline
-> route pipeline
-> receive stream / handler
```

#### 发送链路

```txt
session / sender
-> envelope build
-> send dispatcher
-> scheduler
-> send pipeline
-> protocol encode
-> transport
```

#### 主动流发送

```txt
generator
-> send stream
-> stream envelope(start/chunk/end/error)
-> send dispatcher
```

### 2. Client 数据链路

建议重构后统一为下述形态：

#### 接收链路

```txt
transport / proxy source
-> protocol decode
-> receive dispatcher
-> scheduler
-> receive pipeline
-> route / subscribe sink
-> receive stream / client consumer
```

#### 发送链路

```txt
send / request / watch command
-> send dispatcher
-> scheduler
-> send pipeline
-> protocol encode
-> transport / proxy
```

#### watch / 宿主订阅语义

```txt
watch high-level api
-> subscribe resolver
-> receive stream core
-> optional stream pipeline
-> user consumer
```

### 3. 关键判断

重构后的 `client` 不必和 `server` 拥有相同的外部 API，  
但内部最好都收敛为：

```txt
source -> dispatcher -> scheduler -> pipeline -> route/stream sink
```

这会让：

- plugins 可复用
- scheduler 可复用
- stream state machine 可复用
- middleware 语义保持一致

## 六、哪些能力适合复用

### 1. 适合直接抽成跨端核心

#### pipeline

可复用程度最高，建议优先拆包。

适合包含：

- `composeMiddleware`
- middleware context control 约定
- route matcher
- route middleware merge
- pipeline registry / plugin mount hooks

#### scheduler

强烈建议跨端统一。

原因：

- `server` 已经存在顺序与优先级调度诉求
- `client` 也有接收时序、发送节流、watch 重入等调度需求
- 后续插件、重试、限流都需要统一调度接口

#### dispatcher core

适合抽成“无宿主假设”的内核。

应仅关心：

- context 组装
- scheduler 调度
- middleware 执行
- route middleware 选择
- stream 分发
- transport / sink 调用

#### stream core

适合直接抽成统一内核，但建议拆成两个方向的核心能力：

1. `SendStreamCore`
2. `ReceiveStreamCore`

其中：

- `SendStreamCore` 负责将业务数据生产为流式协议帧
- `ReceiveStreamCore` 负责消费、排队、迭代、停止、结束与错误处理
- `client` 的 `watch / subscribe` 语义应保留在宿主层，不放入 stream 内核

可共享的部分：

- 生命周期状态机
- async iterator / queue 能力
- middleware hook 约定
- stop / end / fail / reject 语义

### 2. 不建议直接抽成同一个公共实现

#### session

`server` 的 `session` 更像连接会话实体，包含：

- `meta`
- `rooms`
- `send / emit / stream`
- 连接状态

`client` 不存在完全对等的概念。  
因此不建议直接复用 `WSSession`。

更合理的做法是：

- `server` 保留 `WSSession`
- `client` 如有需要，未来单独定义 `Connection` / `Endpoint`
- 两者共享底层 dispatcher / stream / scheduler / pipeline

### 3. 关于 stream 的进一步判断

基于当前代码事实，更适合这样理解两端的 stream：

- `server/sendStream` 是发送流核心，负责生产协议流帧
- `server/receiveStream` 是接收消费流核心，负责流式消费模型
- `client/StreamTask` 本质上也更接近消费流模型，而不是单独的一类“订阅流”

因此更推荐的统一方式不是再单独发明一层“订阅流内核”，而是：

- 在 `@ws-flow/stream` 中沉淀 `SendStreamCore`
- 在 `@ws-flow/stream` 中沉淀 `ReceiveStreamCore`
- 将 `client` 的订阅、watch、route 绑定等语义保留在 `client` 宿主层

这样内核只关注：

- 流的生产
- 流的消费
- 生命周期与队列
- middleware 与控制语义

而不关注：

- 订阅从哪里来
- route 如何注册
- watch 如何对外暴露 API

#### route / subscribe API

`client` 的 `on/subscribe/watch` 是高层体验 API。  
`server` 的 `route/handle` 是处理入口 API。  
两者语义接近，但不必做成同一个宿主接口。

## 七、关于 client 数据格式的设计

这是跨端统一中最关键的设计点。

### 1. Server 的数据格式约束是合理的

`server` 作为主控端，可以约束统一 envelope：

```ts
type WSEnvelope<T = any> = {
  event?: string
  data?: T
  streamId?: string
  streamState?: 'start' | 'chunk' | 'end' | 'error'
  priority?: number
  meta?: Record<string, any>
}
```

这样：

- server 内核实现更稳定
- 双端协议流语义可以统一
- stream lifecycle 容易标准化

### 2. Client 不能被强制绑定到 envelope

`client` 需要既能：

- 完整适配 `ws-flow/server`
- 又能单独接通用 websocket 服务

因此 `client` 必须保留协议适配层。

### 3. 建议采用双模式协议方案

#### Strict Mode

面向 `ws-flow/server` 配套场景。

特征：

- 默认使用 `ws-flow envelope`
- 直接支持统一 event / stream / priority / meta 语义
- 无需用户手写复杂解析逻辑

适合目标：

- 双端同构
- 最低接入成本
- 框架完整体验

#### Generic Mode

面向任意 websocket 服务。

特征：

- 通过 protocol / adapter 提供最小必要解析能力
- 用户只在必要时声明如何：
  - encode send
  - decode receive
  - resolve event
  - resolve stream

适合目标：

- 保持独立可用
- 不强制依赖 `ws-flow/server`
- 兼容已有服务端结构

### 4. Protocol 不应消失，而应升级为“Adapter”

建议从“暴露一堆协议函数”升级为更友好的 adapter 形式：

```ts
const client = new WSClient({
  adapter: wsFlowAdapter()
})

const client2 = new WSClient({
  adapter: genericAdapter({
    encodeSend,
    decodeReceive,
    resolveEvent,
    resolveStream
  })
})
```

这样：

- 严格模式用户几乎零配置
- 通用模式用户只配置必要能力
- 架构上依然有协议抽象，不会失去泛化能力

## 八、推荐的拆包方案

建议未来拆为以下层次：

```txt
@ws-flow/pipeline
@ws-flow/scheduler
@ws-flow/stream
@ws-flow/dispatch
@ws-flow/protocol
@ws-flow/server
@ws-flow/client
```

### 1. `@ws-flow/pipeline`

包含：

- compose
- context control contracts
- matcher
- middleware registry
- plugin mount 基础

### 2. `@ws-flow/scheduler`

包含：

- scheduler interface
- composable scheduler
- session/order scheduler
- priority scheduler

### 3. `@ws-flow/stream`

包含：

- send stream core
- receive stream core
- consumer / iterator buffer
- stream middleware hooks
- stream lifecycle contracts

### 4. `@ws-flow/dispatch`

包含：

- send dispatcher core
- receive dispatcher core
- dispatcher deps contracts

### 5. `@ws-flow/protocol`

包含：

- envelope contracts
- strict ws-flow adapter
- generic adapter builder
- encode / decode / resolve contracts

### 6. `@ws-flow/server`

保留：

- `WSServer`
- `WSSession`
- rooms
- server runtime assembly
- websocket server adapter

### 7. `@ws-flow/client`

保留：

- `WSClient`
- `on / once / subscribe / watch / request`
- reconnect / restore
- websocket / proxy adapter

---

## 九、建议的演进顺序

### 第一阶段：先稳定跨端内核边界

优先整理：

1. `pipeline`
2. `scheduler`
3. `stream core`
4. `dispatcher deps contracts`

这是当前最值得优先沉淀的部分。

### 第二阶段：设计 protocol adapter 双模式

先定接口，不急着马上拆包。

目标：

- 明确 strict mode
- 明确 generic mode
- 明确 envelope 作为默认适配协议

### 第三阶段：做 client major 重构

目标不是完全复制 server，而是让 client 内部链路改为：

```txt
source -> dispatcher -> scheduler -> pipeline -> route/stream sink
```

同时保留原本易用的高阶 API。

### 第四阶段：接入 plugins pipeline

plugin 挂点优先放在统一内核层，而不是只挂在 `server/client` 宿主层。

理想挂点包括：

- receive pipeline
- send pipeline
- route middleware
- stream middleware
- observers / lifecycle hooks

---

## 十、当前结论

当前最合适的整体判断是：

1. 现在已经适合开始为 `plugins pipeline` 和 `client major` 重构做统一架构准备。
2. `middleware + pipeline` 非常适合最先拆成跨端核心。
3. `dispatcher / scheduler / stream core` 也适合逐步抽成统一内核。
4. `session` 不建议直接作为跨端公共抽象。
5. `client` 必须保留协议适配层，但要从“底层 protocol 配置”升级为“strict/generic adapter 模式”。
6. 双端真正应统一的是内部数据流模型，而不是表层 API 形式。

最终目标不是把 `server` 搬到 `client`，而是让两侧共享同一套实时通信运行时内核，并在各自宿主层提供最合适的高级体验。
