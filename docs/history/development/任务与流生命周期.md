# 请求任务与流生命周期

> 历史契约草案。单结果、请求流及主动流取消现已落地；当前默认值与边界见[架构编排与设计说明](架构编排与设计说明.md)。

日期：2026-09-20。状态：与《双向通信架构与 API》配套的完整行为契约草案，已部分落地。当前实现以《接收流与连接清理》《单结果请求实现》为准；下文的远端取消、流式请求等仍是目标行为。

适用范围：下文的消息类别是标准 ws-flow 协议的逻辑契约；通用 Client 可以只使用发送和订阅。对自定义协议启用请求 / 流能力时，由 Adapter 提供等价的关联与终止信息，不强制网络消息采用这些类别或字段。远端取消仅在对方协议支持时传播，本地清理始终有效。

## 1. 所有权与身份

- Peer 指一条连接中的远端；连接重建产生新代际 connectionEpoch。
- 所有请求、流和排队任务都归属于 Peer + connectionEpoch，不能跨代际复用。
- 待响应请求表和远端入站任务表分开。双方同时使用相同 requestId 也不应冲突。
- 接收流和发送流分开存储；接收流至少按 Peer + epoch + streamId 索引。
- 消息自身 ID、请求关联 ID、流 ID 分别承担不同职责，不能默认混用。
- ID 由运行时生成，业务无需管理；准确字段名和编码格式在协议实现阶段确定。

## 2. 逻辑消息类别

以下描述必需语义，不冻结 JSON 字段名。

| 类别 | 必需含义 | 接收后的目标 |
| --- | --- | --- |
| 通知 | 可选事件名、业务数据 | 订阅分发 |
| 请求 | 关联 ID、事件名、输入、预期结果模式（单值 / 流） | 入站任务与唯一处理器 |
| 单值成功响应 | 关联 ID、可为空的结果 | 待响应请求 |
| 请求失败响应 | 关联 ID、规范错误 | 待响应请求或尚未开始的流任务 |
| 流 start | streamId、可选请求关联、主动流的事件名 | 建立消费者、绑定请求或交付主动流 |
| 流 chunk | streamId、业务数据 | 对应消费者 |
| 流 end | streamId | 正常终止 |
| 流 error | streamId、规范错误 | 异常终止 |
| 取消请求 | requestId | 对应远端入站任务 |
| 取消主动流 | streamId | 对应远端发送流 |

请求关联 ID 属于发起端命名空间。cancel request 只取消接收端的入站任务，不根据碰巧相同的 ID 取消接收端自己发出的请求。

流式请求在 start 前失败，通过请求失败响应结束；start 后失败，通过流 error 结束。收到与预期结果模式不符的消息时失败为协议错误。

远端错误应使用可序列化结构，例如 code / message / 可选 details。不能直接 JSON.stringify(Error) 后假定 message 会保留；默认不传 stack 或内部实现细节。

## 3. 发起方请求生命周期

```text
created -> pending -> succeeded
                   -> failed
                   -> cancelled
                   -> timed_out
                   -> disconnected
```

pending 覆盖本地排队、发送和等待结果阶段。是否暴露更细状态是 API 层选择。

1. 校验参数与预先已取消的 AbortSignal。
2. 分配关联 ID，在发送前登记 pending 任务和取消监听。
3. 建立 timeout，再进入发送管线与调度器。timeout 包括排队时间，防止队列中的请求永远不结束。
4. 发出消息。发送成功仅表示本地传输完成，不结束请求。
5. 结果到达后按 Peer + epoch + requestId 精确关联。
6. 第一个终态胜出；后续竞争结果不二次完成、不恢复任务。
7. 终态时移除表记录、计时器、监听和排队引用。

发送失败与结果到达可能竞争，采用同一幂等终止入口。排队任务执行前重查存活状态，已超时或取消的请求不能继续发送。

重复 / 迟到响应不得投递给新任务，可报告有限的诊断信息；诊断记录也不能无限增长。

默认 timeout 数值尚未确定，应提供有限、文档化的默认值，并允许明确选择无超时；示例中的 10 秒不是全局默认值。

## 4. 接收方请求生命周期

```text
received -> validated -> queued -> running -> replied
                                            -> failed
                                            -> cancelled
                                            -> disconnected
```

- 权限与结构校验先于 handler 执行。未找到处理器、容量不足、模式不符等均产生关联失败响应。
- 同一连接代际内，正在执行的重复 requestId 不再次运行 handler；报告协议问题。终止记录若缓存，必须有数量和时间上限。
- handler 接收 AbortSignal；远端取消、断连和本地终止会触发 signal。
- 返回业务值后由内核生成响应。正常返回 undefined 也是成功，不能让调用方永久等待。
- handler 抛错转为关联失败，同时可通知 Observer。
- 取消后禁止再次发送正常结果。无法强制终止任意 JS 函数，业务必须协作处理 signal；迟到完成仍应被消费，避免未处理拒绝。
- 响应发送失败时本地清理任务并报告 transport issue，不能承诺远端已知失败。

handler 可以反向调用 peer.request。不得在等待反向响应期间占住该响应必经的调度通道。

## 5. 流式请求与主动流

```text
等待 start -> open -> ended
                  -> failed
                  -> cancelled
                  -> timed_out
                  -> disconnected
```

- 流式请求先建立待关联任务，start 到达后绑定 streamId。
- 主动流 start 到达时建立消费者，并向主动流接收器交付一次流对象。
- 先完成消费者登记，再启动业务消费；帧接收推进不等待整个消费函数完成。
- 同一流内严格遵循 start -> chunk* -> end/error；重复 start、缺失 start、终止后 chunk 都是非法转换。
- 终态只执行一次，终止帧按发送顺序排在此前 chunk 之后。
- 正常 end 后，允许读取已缓冲 chunk，再返回 done。
- error 必须让异步迭代抛错，并保留规范错误信息；建议失败时清空未消费缓冲，下一次读取直接失败。
- cancel / timeout / disconnect 同样使等待中的 next() 失败并清理缓冲；主动调用 iterator.return() 则让本地迭代正常退出，同时发起任务取消。
- for-await 提前 break 会调用 return()，释放消费者与上游资源；不得留下无人消费的永久流。
- 生产侧终止时尽力调用 generator.return() 并通知 AbortSignal。若 generator 正阻塞于不可取消操作，不能保证其立即退出，迟到结果必须被忽略。

流超时区分等待 start、空闲时长和总时长。建议 requestStream 的 timeoutMs 明确表示总期限，另设 idleTimeoutMs；具体默认值待确定，不能在不同 API 中偷偷改变同名选项含义。

## 6. 取消的传播

- 本地取消立即结束本地等待，不依赖远端确认。
- 请求尚未发送时移除 / 跳过本地任务，不需要发送 cancel。
- 已发送且连接可用时，尽力发送取消控制消息。
- 远端收到 cancel 后中止对应 signal、停止后续产出并清理任务。
- 取消不等于撤销已发生的业务副作用，也不提供分布式事务语义。
- 断连时无法保证取消消息到达；本地与远端各自依赖连接生命周期清理。

## 7. 调度约束

将短时的帧接收与关联操作，同长时的业务 handler 执行分开。

- 不同 Peer 默认独立推进，不能由一个全局串行优先级队列锁住所有连接。
- 同一连接上的帧验证 / 关联和同一流上的消费入队保持必要顺序。
- 请求 handler 的并发限制是独立策略；等待响应不占用响应接收所需的唯一执行槽。
- 公共 receive middleware 不应作为长期业务任务的容器；任务处理应进入 handler 执行层。
- priority 只能重排允许重排的任务，不能跨越同一流的因果顺序。
- 取消控制和连接清理不等待业务 handler 完成。
- 调度任务失败必须释放执行槽；空队列键必须回收。
- 运行中替换 scheduler 的迁移策略在实现前明确，不能悄悄丢弃旧队列。

## 8. 缓冲与容量

模块化调度并不等于背压。至少分别配置待执行请求数、订阅队列、流缓冲容量和传输待发送量。

- 默认缓冲应有界；容量单位（条目 / 字节）和默认值在实现时给出。
- 订阅可选择显式丢弃 / 合并策略，例如状态消息保留最新值。
- 请求结果和可靠流分块不能默认静默丢弃。容量不足时拒绝任务或失败并取消上游。
- 跨网络的暂停 / credit 协议属于后续扩展；初版有界缓冲不应宣称实现了完整端到端背压。
- 没有匹配接收器的主动流应有确定的拒绝 / 取消行为，不能无限缓存。

## 9. Pipeline 控制语义建议

| 控制 | 含义 |
| --- | --- |
| drop 当前通知 | 过滤一条通知，不结束订阅 |
| reject 请求 / 结果 | 产生明确失败，不遗留 pending |
| end 流 | 正常结束并发送 / 交付终止信号 |
| fail 流 | 异常结束并传播错误 |
| cancel 任务 | 主动终止并尽力通知远端 |

当前 stop 在不同位置含义不一致。下一版不让同一个 stop 同时代表丢帧和终止整个任务；最终方法名随 API 评审确定。可靠流 chunk 的任意过滤会改变业务内容，必须是显式选择。

## 10. 连接与运行时清理

Runtime 提供统一的 closePeer / dispose 类内部入口（名称待定）：

1. 阻止新任务进入该连接代际。
2. 结束所有 pending 请求、入站任务和双向流。
3. 移除计时器、取消监听、排队引用与连接局部订阅。
4. Server 清理房间与 socket 绑定；Client 根据独立策略保留可恢复的订阅描述。
5. 全部步骤幂等。dispose 还应解除宿主级 connection 监听与插件资源。

takeover 不拥有外部 WebSocketServer 本身，但拥有自己添加的监听和任务。解除托管与关闭连接应明确区分。

## 11. 必须覆盖的验收场景

| 场景 | 预期 |
| --- | --- |
| 双方同时发起请求，ID 恰好相同 | 分别正确关联 |
| 两连接使用相同 streamId | 数据与终止状态完全隔离 |
| 同事件的并发请求乱序返回 | 每个调用取得自身结果 |
| 响应先于 send Promise 完成 | 不丢结果、不重复结算 |
| handler 返回 undefined / 抛错 / 未注册 | 调用方均得到明确结算 |
| handler 中反向请求并 await | 接收响应可继续推进，无死锁 |
| handler 中 for-await 消费流 | 后续帧持续推进，无死锁 |
| timeout 与响应同时发生 | 恰好一次终态，资源归零 |
| 排队期间取消 / 超时 | 不再发送过期请求 |
| 远端 error、提前 break、断连 | 迭代器按契约结束或抛错，资源释放 |
| 流结束帧与不同优先级 chunk | 顺序不被破坏 |
| 慢消费者 / 未消费流 | 缓冲有界且有明确处置 |
| 某订阅或 Observer 抛错 | 其他订阅与关联任务不受影响 |
| 重连后迟到旧响应 | 不交付给新代际任务 |
| 多目标部分失败 / 空集合 / 调用取消 | 按目标独立结算，无遗留任务 |
