# 流式请求实现

> 本页保留流式请求阶段记录。新 Client 已迁入共同内核；当前双端 API 见[架构编排与设计说明](架构编排与设计说明.md)与[Client迁移与使用](Client迁移与使用.md)。

2026-09-20。已接入 RuntimeCore 和 Server；旧 WSClient 尚未迁入。

## 调用与处理

```ts
server.handleStream<{ count: number }, number>('numbers', async function* (ctx) {
  for (let n = 0; n < ctx.data.count; n++) {
    if (ctx.signal.aborted) return
    yield n
  }
})

// 向实现了配套请求协议的客户端发起请求。
const task = session.requestStream<number>('measurements', {}, {
  timeoutMs: 30_000,
  capacity: 128,
})
try {
  for await (const sample of task) {
    console.log(sample)
    if (sample > 100) break
  }
} catch (error) { console.error(error) }
```

`requestStream()` 立即返回 StreamTask，而不是 Promise。可通过 next / for-await 消费，通过 cancel(reason?) 显式取消，通过 state / closed 查看本地状态。state 为 waiting、open、ended、failed 或 cancelled；AbortSignal、超时、断连按失败终态处理，显式 cancel 和提前 return 为 cancelled。

共享内核入口为 `runtime.requestStream<Chunk>(peer, event, input, options)`、`runtime.handleStream<Input, Chunk>(event, handler, peer?)`。Server 与 Session 均可 handleStream，Session 局部注册优先，注销函数幂等。handleStream 和 handleRequest 共用事件命名空间，不能在同一作用域重复注册。

handleStream 必须返回 AsyncGenerator，或解析为 AsyncGenerator 的 Promise。它可以先异步准备资源，再返回生成器。单值与流的模式不匹配会返回 MODE_MISMATCH，不根据业务返回值猜测模式。旧 session.stream 继续表示主动发送流，不等同于请求结果流。

## 协议与执行路径

请求仍为 kind=request，通过 resultMode=stream 声明预期结果；未声明 resultMode 的请求保持单值兼容。

结果帧使用 kind=request_stream，每帧携带 requestId、streamId 和 streamState。生命周期是 start → chunk* → end/error。首帧必须 start；后续不能重复 start 或更换 streamId。按 Peer 对象身份和 requestId 关联，每个任务独立接收缓冲，不进入普通订阅和旧事件路由。

handler 在建立发送流前失败时发送 request_error；发送 start 后，生产或处理失败通过 streamState=error 传播。错误采用 code / message，保留到远端迭代器抛出的 RequestError。未知或已结束请求的迟到流帧被忽略。

Adapter 使用 `request.write` 编码请求、`request.stream.write` 编码结果帧、`request.cancel.write` 编码可选取消。三者由自定义协议分别声明；请求流不要求具备主动推送流的 stream.write。标准 Adapter 默认提供这些能力。ID、缓冲、期限、取消状态仍由内核维护。

生产方复用 SendStream、消费方复用 ReceiveStream，经过已有发送 / 接收流中间件和普通收发中间件。控制字段 kind、requestId、resultMode、streamId、streamState 不允许由普通收发中间件重写；业务数据可变换。流中间件的 end / fail 继续控制流终态。

## 结束与回收

- 默认 capacity=128 个 chunk，正整数配置。超过缓冲上限明确失败并尽力通知生产方取消，不静默丢失数据。非法 capacity 在创建时同步抛错。
- 正常 end 后可读完缓冲；error、超时和断连清空未消费数据，使等待中和未来的 next 拒绝。
- for-await 提前 break / return 会丢弃本地缓冲并正常结束迭代，同时尽力通知远端取消。显式 cancel 则使未完成读取失败。
- 请求开始前发送失败、协议能力缺失和参数错误通过任务读取失败体现；内部 Promise 的拒绝已接管，不要求调用方额外处理后台 Promise。
- timeoutMs 是从请求登记起的总期限，包含排队、发送、等待 start 和消费中的时间。默认 30000ms；null 显式关闭。没有独立 idleTimeoutMs。
- 取消、超时、接收中间件提前结束或消费溢出复用 request_cancel；远端收到后中止 handler.signal、请求 generator.return，并阻止后续帧。缺少取消编码能力时只做本地终止。
- handler 尚在准备生成器时取消，后续返回的生成器也会收到 return，不再发送 start。generator 内部任意 await 无法强制中断，finally 可能推迟执行。
- 正常终态、失败、取消和断连均注销请求记录及期限监听；单值与流式请求共用每连接 1024 条待响应 / 入站活动名额。

## 当前边界

本轮是可用的单连接流式请求基线，尚无空闲期限、按字节缓冲、协议级背压、多目标流聚合或主动流远端取消。取消消息仍可能被中间件或传输队列阻塞，不保证送达，也不会撤销业务副作用。

调用方不消费且不取消的流最多缓存 capacity 条数据，并受默认总期限限制；timeoutMs=null 时应由业务承担明确的终止责任。流中间件的 stop 沿用既有逐帧过滤语义，不能将其视为可靠流的无损背压。

正常结束的任务若仍被应用持有，会保留未读取的缓冲；调用 return 可丢弃它。只有本地任务 state=ended 并不代表业务已处理完所有缓冲数据。
