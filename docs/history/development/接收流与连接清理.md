# 接收流与连接清理

> 本页保留早期实现记录。主动流远端取消现已实现；当前完整状态见[架构编排与设计说明](架构编排与设计说明.md)。

2026-09-20。本页描述已经实现的行为，不代表完整请求与取消协议已经完成。

## 消费与帧推进

接收流按 Peer 对象身份和 streamId 共同索引；不同连接使用相同 streamId 不会混入同一消费者。活动流重复 start 会报告 duplicate_start，不覆盖已有流。没有活动流的 chunk / end / error 报告 missing_start。

start 启动事件处理函数，但接收调度不等待该函数的整个生命周期。因此处理函数可以直接 `for await (const chunk of ctx.stream)`，后续帧仍能进入接收队列。dispatch(start) 完成只表示该帧处理完成，不表示业务处理结束。异步处理函数失败经 RuntimeCore.useStreamErrorObserver 报告；Server 对应 process_error。

接收与流中间件仍属于帧处理流程，应及时完成；不要在这些中间件中等待同一连接的未来消息。异步消费放到事件处理函数中。

Server 默认入站和出站均使用 SessionScheduler，同一连接按提交顺序执行，不同连接独立推进。原先默认组合中的全局优先级串行调度已移除；自定义调度器仍可配置，但需要自行保证流帧顺序。

## 消费者终态与缓冲

- StreamConsumer 默认最多缓冲 128 个 chunk；直接构造消费者或 ReceiveStream 时可指定 capacity。Server 尚未暴露该配置。
- 溢出会失败并清空缓冲，等待中的 next 和后续 next 都拒绝，不静默丢弃。
- 正常 end 允许读完已缓存的数据；远端 error 传递错误值并清空缓存。
- for-await 提前 break 会调用 return，丢弃剩余缓存、结束本地流并注销流记录。这尚不发送远端取消命令。
- onData 回调消费和异步迭代是两种互斥模式。回调模式不会额外积累无人读取的迭代队列；异步回调不提供背压，需等待的顺序处理应使用 for-await。
- 终态清理流记录、回调和本地流中间件；业务仍持有的流对象可以读取正常结束前的缓存。

## 连接关闭

宿主断开连接时调用 runtime.closePeer(peer)：使其活动接收流失败、结束绑定该 Peer 的订阅，并拒绝该连接后续收发。接收或发送中间件等待期间发生关闭，在中间件恢复后也会重新检查，避免继续投递。跨连接订阅继续存在。

runtime.dispose() 关闭全部接收流与订阅、取消已登记的发送流，并禁止继续收发和创建订阅。closePeer 同样取消该 Peer 的发送流。两者均可重复调用。

Server 已接入该入口：socket 断开、detach、server.close 会清理会话、房间和关联监听。detach 不关闭外部 socket，但该 Session 不再可用。takeover 的 server.close 移除自身 connection 监听并关闭已接管会话，保留外部 WebSocketServer 本身。

## 发送流的本地取消

RuntimeCore 登记 createSendStream 创建的发送流，终态即注销。发送流提供 cancel(reason?) 和 isClosed()；创建后不再使用的流应显式取消，避免保留闲置记录。

Server 的 session.stream 已支持传入 AbortSignal：

```ts
const controller = new AbortController()
const task = session.stream('progress', async function* () {
  yield { percent: 10 }
  yield { percent: 100 }
}, { signal: controller.signal })

// 在需要停止任务时调用；调用方仍需处理 task 的拒绝。
controller.abort(new Error('用户取消'))
try { await task } catch (error) { console.error(error) }
```

- 断连、dispose 或显式取消会使正在等待数据、发送中间件或 transport 的流任务及时拒绝。取消一个流不会关闭连接或影响其他流。
- 取消后尚未送入 transport 的帧不会继续发送；已进入 transport 的发送无法撤回。
- 发送失败、取消或中间件提前结束会请求 generator.return()，且每个任务最多请求一次。首次 start 发送失败也会请求清理。
- JavaScript 无法强制中断生成器内部任意 await。任务拒绝不等于 finally 已执行；只有内部等待恢复，生成器才有机会处理 return。需要及时释放外部资源时，数据源自身也应使用同一个 AbortSignal。
- 清理过程的失败不覆盖原始任务错误；清理返回的 Promise 会被观察，但不阻塞任务结算。未开始执行的原生异步生成器不会执行函数体内的 finally。
- 数据源抛错会尝试发送 error 帧，并保留原始错误作为任务失败原因，即使 error 帧发送也失败。
- 普通 send / emit 的 options 同样支持 signal：取消等待并阻止尚未进入 transport 的发送，不撤回已发出的消息。

取消目前只结束本地任务，不发送远端 cancel / end。若 start 已送达，远端可能继续保留接收流，直到断连或应用自行处理。请勿将本地取消当成完整双端取消。

## 尚未完成

关闭不能强制中断用户自己的 Promise、生成器或已进入 transport 的发送；任意自定义调度队列也不会被强制清空。当前可及时结算发送流任务，但底层操作仍需协作退出，普通未带 signal 的发送也不承诺即时结算。

单流缓存已有上限，但同时活动的流数量、流空闲超时和调度队列总容量尚未限制。请求关联、远端取消和协议背压也未实现，不能据此宣称完整任务生命周期已经完成。
