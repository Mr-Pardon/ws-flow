# 资源控制设计与验收边界

状态：等待队列条数、字节限额、发送水位、登记中的活动任务上限和执行/空闲期限已实现，见[队列限额与取消](队列限额与取消.md)、[字节限额与发送水位](字节限额与发送水位.md)和[活动任务限额与期限](活动任务限额与期限.md)。首版保留这些已有能力，重点验证它们能正确失败和清理，不继续扩充资源控制模型。消费对象字节估算、端到端确认窗口与持续压力矩阵留待后续评估。

## 目标与分层

配置了限额的维度应保证积压有上限、超限能明确失败、关闭能回收、异常可观察。按消息条数限制 consumer 只覆盖消费层，无法约束 socket、解码队列与调度队列。不能将资源控制全部放入 Scheduler。

| 层 | 负责限制 | 超限策略 | 资源所有者 |
| --- | --- | --- | --- |
| 宿主入站 | 重组后的原始消息大小、解码与分发积压条数/字节数 | 拒绝新消息并关闭该连接，结算任务 | Server/Client |
| 内核调度 | 全局及每 Peer 待执行任务数 | 拒绝新任务，不能静默丢控制帧 | 调度器/运行时 |
| 请求与主动流 | 入站/出站请求数、活动流数、执行/空闲期限 | 明确拒绝或取消具体任务 | RuntimeCore |
| 消费队列 | 每订阅/流的缓冲条数 | 失败并释放对应消费者，必要时远端取消 | consumer / subscription |
| 宿主出站 | 编码后消息大小、待发送字节与底层 bufferedAmount | 达到高水位暂停，降至低水位恢复；等待有期限 | transport |

基础调度器只接受短任务，不读取业务 payload。传输字节数在 codec 前后由宿主计算；消费对象未做字节估算，不能宣称 JS 堆内存可精确计量。首版无需为此新增 sizeOf 接口。

## 有界入场与明确失败

等待队列与活动任务分别计数。容量超限、任务期限和传输限制已有独立错误类型；Server 的 issue observer 提供 Peer、错误及适用的方向/任务类别，Client 的 onIssue 提供错误。错误字段按类型携带限额或期限，不记录完整业务载荷。

计数应在接受工作时预留，在成功、异常、取消或关闭时恰好释放一次。全局额度与 Peer 额度必须一起检查，拒绝不能留下部分预留。区分等待数量和运行数量，避免把 concurrency 当成 queue capacity。

配置容量为有限正安全整数；NaN/Infinity/0 不是有效限额。订阅/接收流默认缓冲 128 条，每 Peer 每方向默认最多 1024 个请求；其他未配置的限额维度不限制。首版保留这些现有默认值并说明作用，不再加入未经测量的通用容量预设。

## 关闭和取消不被普通工作阻塞

满队列不能静默丢弃取消/终态。当前任务控制帧的入场失败按致命队列/传输错误关闭连接，使关联任务按断连结算，不另设控制消息保留额度。必须保持同任务因果顺序：取消不能在其 start/request 之前到达，不允许通过优先级重排破坏帧顺序。

若无法接受必要控制帧，宿主应关闭该连接，使所有任务按断连结算。不要让消费者溢出后仍继续无限接收并解码。调度器需支持移除未开始任务，已运行的任意用户 Promise 仍然只能协作取消。

## 期限与发送水位

请求保留总期限；入站执行期限和流空闲期限独立配置。空闲期限从有效进度更新，收到无关消息不能续期；超时取消进入现有单一终态通道。

当前配置为 taskTimeouts.incomingRequestMs 与 streamIdleMs，均默认关闭。前者从入站请求被接受后开始，后者用于所有流对象；接收方从 start 开始，发送方从流对象分配开始，只有有效进度更新。taskLimits 将请求（包含请求流）与主动流分为四个方向类别，并共享全局/每 Peer 上限；响应和取消不另外占任务额度。达到任务额度时只拒绝新任务，通知对端失败/取消的控制消息仍受原有发送队列和字节保护。

活动计数覆盖内核的逻辑登记，不是用户代码实际运行数量。超时/取消及时释放任务并通知 signal，但无合作的用户 Promise 可能继续保留资源；由于帧调度器不等待业务处理器全生命周期，仅调小调度并发数也不能限制这类工作，必要时业务侧应单独管理执行池。

浏览器 send 无应用层 drain 通知，水位检查需要受控的唤醒机制和等待期限；Node send callback 也不能作为对端消费确认。编码后一次性提交与取消可能竞争，应记录是否进入传输，保持取消语义。

发送水位现已落地：宿主在发送调度后编码并预留字节，`transport.prepare` 等待水位，随后内核标记进入传输并提交。启用水位时，同一 Peer 的准入一直串行到实际 send 完成，防止自定义并发调度器重复使用相同的缓冲余量。期限从开始检查水位计算，不覆盖此前的调度或准入等待；请求仍有自身总期限。字节额度不计调度队列中未编码的对象，亦不代替 `ws.maxPayload` 等解析器限制。

## 首版有限验收

- 复用已有慢解码、慢中间件、慢消费者及水位等待回归，确认配置的限制真实生效。
- 一个 Peer 达到上限不会耗尽其他 Peer 的独立额度，全局上限仍可限制总积压。
- 队列已满时 abort/close/timeout 能结算，并正确释放全部预留与计时器。
- 发送等待期间断连、新连接建立后，旧帧不得继续提交到新连接。
- 补少量重复连接/断连及请求、流、取消组合，检查结束后的活动计数与受控队列，不建立长时间跑分系统。
- 对同任务检查 start → chunk → terminal 的顺序，不因调度优先级出现倒序。

验收发现的泄漏、错序、重复结算与跨连接串扰属于现有模型缺陷，首版必须修复。有限用例通过后进入发布准备；完整跨平台/多浏览器/Worker 矩阵、大量连接、长时间压力、重连风暴和 RSS 趋势测量不作为首版前置条件。RSS 只能作为辅助指标，不能据此宣称 GC 会立即回到起点。

端到端消费确认、流窗口和断点恢复会修改协议，留待有真实需求时单独设计。首版交付范围见[发版评估](发版评估.md)。
